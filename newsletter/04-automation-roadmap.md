# 04. 자동화 로드맵

## 목표 파이프라인 (최종 형태)

```
[수집]                    [가공]                     [검수]            [배포]
venue 캘린더 크롤러 ─┐
뉴스 검색/RSS ───────┼─▶ 정규화·중복 제거 ─▶ AI 요약/분류 ─▶ 초안 MD 생성 ─▶ 담당자 확인 ─▶ 메일/메신저 발송
동종 업체 페이지 감시 ┘     (data/*.json)        (섹션별 배치)     (issues/)        (PR 승인)        + 아카이브
```

## 단계별 계획

### Phase 0 — 기획 (현재)
- [x] 기획/소스/배포/로드맵 문서 작성
- [ ] 미결 사항 확정 (주기, 채널, 이름, 담당자) — [README](README.md#미결-사항-open-questions)
- [ ] 소스 URL 실제 검증 (`02-sources.md`의 검증일 채우기)
- [ ] 자사 소개서 반영

### Phase 1 — 수동 운영 (1~3호)
- 템플릿(`templates/newsletter-template.md`)으로 사람이 직접 작성
- **이 단계의 진짜 목적: 자동화할 작업을 관찰하는 것**
  - 각 섹션에 몇 분 걸렸는지 기록 → 자동화 우선순위 근거
  - venue 사이트별로 일정 정보가 어떤 형태(HTML 표 / JS 렌더링 / PDF / API)인지 기록
- 산출물: 발행본 2~3개, 섹션별 소요 시간 메모, 독자 피드백

### Phase 2 — 반자동 (수집 자동화 + 사람 작성)
Git 프로젝트 생성 시점. 우선순위는 **반복적이고 규칙적인 것부터**:

| 순서 | 작업 | 방법 | 이유 |
|---|---|---|---|
| 1 ✅ | Venue 캘린더 수집 (2026-10 선행 구현: [collect_venues.py](scripts/collect_venues.py), 5곳) | venue별 수집기 (Python: requests/BeautifulSoup, JS 렌더링 페이지는 Playwright) → `data/events/YYYY-MM.json` | 가장 기계적이고 시간이 많이 드는 작업 |
| 2 ✅ | 캘린더 표 자동 생성 (같은 스크립트가 `.md` 출력) | JSON → 마크다운 표 변환 스크립트 | 섹션 3 완전 자동화, 주간 단신 가능해짐 |
| 3 | 뉴스 후보 수집 | 키워드 기반 뉴스 검색/RSS → 후보 리스트 (제목·링크·날짜) | 사람이 고르기만 하면 됨 |
| 4 | 동종 업체 변경 감지 | 지정 페이지(공지/블로그/릴리스노트) 주기적 스냅샷 후 변경 시 알림 | 놓치는 소식 방지 |

공통 데이터 형식 (예시):
```json
{
  "venue": "COEX",
  "hall": "A홀",
  "title": "행사명",
  "category": "전시회",
  "start_date": "2026-11-05",
  "end_date": "2026-11-08",
  "url": "https://...",
  "source": "coex.co.kr",
  "collected_at": "2026-10-27T09:00:00+09:00",
  "is_our_client": false
}
```

### Phase 3 — 자동화 (초안 생성 + 승인 후 발송)
- **예약 실행**: GitHub Actions 크론 (예: 주간 단신 매주 월 08:00, 월간 본편 초안 매월 마지막 주 수요일)
- **AI 요약**: 수집된 뉴스·업체 소식을 LLM(Claude API 등)으로 섹션별 2~3줄 요약 + "왜 중요한지" 초안 작성
  - 섹션 5(시사점)는 AI 초안 + **반드시 사람이 최종 작성** (자사 상황 판단이 필요)
- **검수 흐름**: 초안을 `issues/`에 PR로 올림 → 담당자가 수정·승인(merge) → merge 시 발송 워크플로 실행
- **발송**: 마크다운 → HTML 메일 변환 후 발송, 메신저 Webhook으로 요약+링크 게시
- **아카이브**: 발행본을 정적 웹페이지로 게시 (현재 저장소처럼 HTML 페이지 활용 가능)

## 리스크와 대응

| 리스크 | 대응 |
|---|---|
| venue 사이트 개편으로 수집기 고장 | 수집 결과 0건이면 알림, venue별 수집기 분리 |
| 크롤링 정책/약관 | robots.txt·이용약관 확인, 요청 빈도 최소화(주 1회), 공공 API 우선 |
| AI 요약의 사실 오류 | 원문 링크 필수, 사람 검수 단계를 생략하지 않음 |
| 경쟁사 서술 리스크 | 공개 정보만, 검수자 확인 |
| 담당자 부재 시 발행 중단 | Phase 3 이후 주간 단신은 승인 없이 자동 발송 옵션 고려 |

## Git 프로젝트 생성 시 예상 구조
```
mice-newsletter/
├── docs/                 # 현재 newsletter/*.md 문서 이관
├── templates/            # 마크다운/HTML 메일 템플릿
├── collectors/           # venue별·소스별 수집기
│   ├── coex.py
│   ├── kintex.py
│   ├── bexco.py
│   └── coex_magok.py
├── data/
│   ├── sources.yaml
│   └── events/           # 수집 결과 JSON
├── issues/               # 발행본 아카이브
├── scripts/              # 표 생성, 요약, 발송
└── .github/workflows/    # 예약 실행, 발송
```
